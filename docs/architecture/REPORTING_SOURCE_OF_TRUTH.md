# Karatu Reporting & Academic Reports — Source of Truth

## 1. Purpose

Reporting presents authoritative academic results.

Reporting does not independently calculate academic results.

The authoritative chain is:

```text
Assessment
    ↓
Calculation Engine
    ↓
Final Results
    ↓
Review / Approval
    ↓
Publication
    ↓
Report Snapshot
    ↓
PDF / Parent Portal
```

---

# 2. Report Identity

A report should be associated with:

- school
- student
- academic year
- term
- grade/class
- section where applicable
- report template
- result version/snapshot

---

# 3. Report Sections

A configurable academic report may contain:

## School Identity

- logo
- school name
- address
- contact information
- motto
- academic year
- term
- report title

## Student Information

- student name
- student ID
- class
- section
- academic year
- term
- optional gender
- optional date of birth

## Academic Performance

Example:

```text
Subject | CA/SBA | Exam | Total | Grade | Remark
```

Columns must be generated from school configuration.

Do not hard-code one universal assessment structure.

## Overall Performance

Possible metrics:

- subjects taken
- subjects passed
- subjects requiring support
- total score
- average
- overall grade
- aggregate

Only configured metrics should appear.

## Attendance

Possible fields:

- school days
- present
- absent
- late
- attendance rate

Attendance data must come from the Attendance domain.

## Conduct

Optional:

- punctuality
- attitude
- cooperation
- respect
- participation
- narrative comment

## Teacher Comment

Teacher comment is entered through the academic workflow.

## Headteacher/Admin Comment

Optional separate administrative comment.

## Promotion

Possible outcomes:

- PROMOTED
- PROMOTED_WITH_SUPPORT
- CONDITIONAL_PROMOTION
- REPEAT
- PENDING_DECISION

Promotion must not be inferred from an arbitrary average unless the school's promotion policy explicitly defines such behavior.

---

# 4. Ranking

Ranking is optional.

Possible modes:

- none
- class
- section
- grade/year-group

Ranking must use the appropriate published result set.

Draft results must never appear in official published rankings.

---

# 5. Learning Outcomes

The report architecture should support:

- learning outcomes
- competencies
- indicators
- achievement status
- teacher comments

This may be optional in initial report templates.

The architecture should not prevent future competency-based reporting.

---

# 6. Report Templates

Schools should be able to configure report templates.

Possible sections:

```text
Academic Results
Attendance
Ranking
Behaviour
Competencies
Teacher Comment
Headteacher Comment
Promotion
Signatures
```

School A may display ranking.

School B may hide ranking and display competencies.

Templates are presentation/configuration concerns.

They must not change authoritative academic results.

---

# 7. Calculation Authority

The Reporting domain must not recalculate:

- assessment scores
- weighted results
- grades
- positions

It consumes authoritative published results.

If the report needs a calculated metric, that calculation must have a clearly defined owner.

---

# 8. Report Snapshots

Historical reports must be reproducible.

A report snapshot should capture:

- student
- school
- academic year
- term
- published result state
- result/version reference
- report template/version
- generated timestamp
- generated by
- publication timestamp

A historical report must not silently change because:

- grading policy changed
- assessment was corrected
- report template changed
- student data changed later

---

# 9. Report Versioning

If a published result is corrected:

```text
Report Version 1
       ↓
Authorized correction
       ↓
Report Version 2
```

Version 1 should remain traceable.

The latest authorized report may become the active report, but historical versions must remain auditable according to school policy.

---

# 10. Report Lifecycle

```text
DRAFT RESULTS
      ↓
SUBMITTED
      ↓
REVIEWED
      ↓
PUBLISHED
      ↓
REPORT GENERATED
      ↓
REPORT AVAILABLE
```

Teachers must not generate official reports from draft results.

---

# 11. PDF Generation

PDF generation should occur from an authoritative report snapshot.

Conceptually:

```text
Published Results
       ↓
Report Generation Service
       ↓
Report Snapshot
       ↓
Template
       ↓
PDF Generator
       ↓
Private Report Storage
```

Generated PDFs must use tenant-scoped private storage.

---

# 12. Parent Portal

Parents should be able to:

- view published reports
- view academic performance
- view attendance
- view comments
- download reports

Parent access is relationship-based.

A parent can only view reports belonging to their children.

---

# 13. Bulk Generation

Authorized administrators should be able to generate reports for:

- one student
- one class
- one section
- an academic year/term scope

Bulk generation should show:

- number eligible
- number generated
- number pending
- number failed
- reason for failures

The operation should be observable and auditable.

---

# 14. Report Publication

Report generation and report publication are related but distinct operations.

A report may be generated internally before being made visible to parents.

Publication must only expose reports based on authoritative published results.

---

# 15. Finance Relationship

Finance may optionally contribute a configured status such as:

```text
Fees: Up to date
```

or:

```text
Outstanding Balance: GHS X
```

Academic report publication must not automatically be blocked because of unpaid fees.

Any financial restriction must be an explicit school policy.

---

# 16. Auditability

Audit:

- report generation
- report publication
- report withdrawal where supported
- report regeneration
- template changes
- report correction
- bulk report generation
- parent report access where policy requires

---

# 17. Tenant Isolation

Every report is tenant-owned.

Report identifiers, PDFs, snapshots, and downloads must be tenant-scoped.

A report URL must never be sufficient to bypass authorization.

---

# 18. Core Principle

> A report is a presentation of authoritative published results, not a second calculation system.

The Reporting domain consumes authoritative academic data and produces reproducible, configurable, auditable outputs.
